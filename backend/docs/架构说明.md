# 线上洗车平台 v6.0 · 架构说明

> 本文说明 SSM 分层架构、请求处理链路，以及 V1 测试版中 **模拟支付 / 缓存分级 / 认证门槛** 的实现口径。
> 业务域清单见 `模块清单.md`；部署与运行见 `../DEPLOY.md`。
> 后端 Java 代码由后端工程师实现，文中类/包路径为**约定落点**（`com.xiche.<业务域>.*`），最终以实际代码为准。

---

## 1. 架构模式与部署形态

**选择：前后端分离的单体（模块化单体），war 部署。**

判据：

- 产品为 V1 内部测试版，日活预期千级以内 → **不上微服务、不上分布式事务、不上多级缓存集群**；
- 三端（小程序 / App / H5）共用一套后端 API → 后端独立成 war，前端独立工程；
- 5 个 Maven 模块实现清晰分包，具备"模块化单体"边界，未来高负载模块可按需拆分。

拓扑：

```
小程序 / App / H5 / 后台Web
          │  HTTP（V1 局域网；生产须 HTTPS）
          ▼
     Tomcat 9（单个 war：xiche-web → ROOT.war）
          │  Spring + SpringMVC + MyBatis
          ▼
     MySQL 8（单库，xiche）
          │
          └── 演进项：Redis（缓存/会话）、CDN、对象存储、第三方支付/短信
```

> V1 不部署 Redis 集群与 CDN；PRD v6 定义的分级缓存是**目标设计**，V1 以简化实现落地（见第 5 节）。

## 2. SSM 分层架构

| 层 | 技术 | 落点 | 职责 |
|----|------|------|------|
| 表现层 | SpringMVC 5 | `xiche-web/.../controller/` | 接收请求、参数校验、调用 Service、返回统一响应 |
| 业务层 | Spring 5 | `xiche-service/.../service/impl/` | 业务规则、事务边界、状态机、权限与资格校验 |
| 持久层 | MyBatis 3 + Druid | `xiche-dao/.../dao/` + `mapper/*.xml` | SQL 映射、参数化查询、连接池 |
| 实体层 | POJO | `xiche-pojo/.../entity/` | Entity / DTO / VO，跨层传递 |
| 公共层 | 工具类 | `xiche-common/.../` | 常量、枚举、错误码、全局异常、工具 |

**关键配置**：`applicationContext.xml`（IoC / 组件扫描 / 事务 / SqlSessionFactory / Mapper 扫描）、`spring-mvc.xml`（HandlerMapping / JSON 转换器 / 视图解析）、`mybatis-config.xml`（MyBatis 全局设置 / 类型别名）、`jdbc.properties`（连接参数）、`logback.xml`（日志）。均在 `xiche-web/src/main/resources/`。

**统一响应体**：`{ "code": 0|200, "msg": "...", "data": {...} }`。前端 `utils/api.js` 按 `SUCCESS_CODES = [0, 200]` 解包，401 清除登录态。

## 3. 请求处理链路

```
客户端（小程序/App/H5/后台）
   │  GET/POST /api/...  +  Authorization: Bearer <JWT>
   ▼
Tomcat 9  ──▶ SpringMVC DispatcherServlet（前端控制器）
   │
   ├─▶ HandlerMapping 匹配 Controller 方法
   ├─▶ 拦截器链（AuthInterceptor：JWT 校验 → RBAC 功能权限 → 数据范围 Scope）
   ├─▶ HandlerAdapter 调用 Controller（参数绑定 / @Valid 校验）
   │      ▼
   │   Service（@Transactional 事务边界；业务规则 / 状态机 / 资格谓词）
   │      ▼
   │   Mapper 接口 ──▶ MyBatis XML（参数化 SQL，强制拼接 Scope 的 WHERE 条件）
   │      ▼
   │   MySQL 8（Druid 连接池；慢 SQL 记录）
   │
   ▼  统一响应 {code,msg,data} ──▶ Jackson 序列化 JSON ──▶ 客户端解包
```

**异常链路**：业务异常 → 全局异常处理器（`xiche-common/exception/`）→ 转 `{code,msg}` 返回；**禁止用 200 包一切错误**，4xx 客户端问题、5xx 服务端问题分段定义。

## 4. 模拟支付如何实现（V1）

**口径**：V1 所有支付为**模拟支付**，仅产生测试流水与状态变更，**不接任何真实支付渠道、不产生真实资金收付**。

实现要点（约定落点 `xiche-service/.../payment/service/impl/` 与 `xiche-dao/.../payment/`）：

1. **入口**：订单确认后调用 `MockPaymentService.createPayment(orderId, amountFen)`；
2. **金额**：一律以**整型分**传输与存储（`amount_fen`），禁止浮点；前端 `fen2Yuan()` 展示；
3. **状态机**：`CREATED → PAYING → SUCCESS / CLOSED`，状态流转写入支付流水表与审计日志；
4. **幂等**：客户端生成 `requestId`，服务端唯一索引去重，重复回调不重复入账；
5. **回调**：内部模拟回调（非外部 HTTP），成功后驱动订单状态机推进；失败保留可解释原因；
6. **前端约束**：成功文案固定为橙色「模拟支付成功」，严禁绿色「支付成功」；小程序常量见 `clients/miniprogram/utils/constants.js`。

**生产演进**：替换 `PaymentService` 实现为持牌支付机构的真实渠道（微信/支付宝/聚合支付），分账由持牌主体完成，回调继续复用幂等逻辑；前端文案与资质同步切换。**此项不在 V1 交付范围**（见 DEPLOY.md 第 10 节）。

## 5. 缓存分级如何实现

### 5.1 PRD v6 目标设计

PRD 第 2~4 章定义**四层缓存**与**三级数据分级**：

| 层 | 职责 |
|----|------|
| CDN | 静态资源加速 |
| L1 本地缓存 | 进程内热点，超短 TTL |
| L2 Redis | 分布式共享缓存、会话与榜单 |
| 网关限流 / 熔断 + 布隆 / 空值防护 | 防穿透、防击穿、防雪崩 |

数据分级：不同实体按"变更频率 × 一致性要求"决定驻留层与 TTL；统一「基础 TTL + 随机偏移」，**禁止固定过期时间**。

### 5.2 V1 落地口径（避免过度设计）

- 单机部署，**不引入 Redis / CDN**；以 `com.xiche.cache` 包的轻量本地缓存 + MyBatis 一级/二级缓存承载热点；
- 缓存键规范统一：`业务域:实体:ID:版本`，例：`catalog:pkg:PKG-02:pv7`、`cert:worker:W123:cv3`、`store:info:S456:v2`（PRD 第 3.3 节）；
- 版本变更通过失效事件主动清除，避免长 TTL 造成脏读；
- 降级：缓存异常时**回源数据库**（fail-open 到主库），保证功能可用。

### 5.3 一致性硬约束

1. **快照固化**：订单创建时固化 `price_snapshot` / `rate_snapshot`，缓存版本变更**不影响已生成订单**，禁止追溯改价/改比例（PRD 第 3.3 节）；
2. **二次核对主库**：派单资格判定中，认证状态仅作候选筛选，**最终接单前二次核对主库**，避免短 TTL 缓存导致未认证接单（PRD 第 6.1 节 / RK-41）；
3. **主动失效**：证书状态、认证等级变更时主动失效派单缓存。

## 6. 认证门槛如何实现（RBAC + 资格谓词）

### 6.1 RBAC 模型与三维权限

模型：`用户 → 角色（支持继承）→ 权限（菜单/按钮/接口）→ 资源`，另引入 **Scope（数据范围）** 作为角色生效边界。新账号一律落**最低权限默认角色**，提权走审批留痕。约定落点：`xiche-service/.../auth/`、`xiche-web/.../interceptor/AuthInterceptor.java`。

**三维权限**（前端隐藏只是礼貌，后端校验才是底线）：

| 维度 | 实现 |
|------|------|
| 功能权限 | 菜单可见 / 按钮可点 / 接口可调用；网关层与业务层**双重校验** |
| 数据权限 | 行级隔离（全部 / 本城市 / 本门店 / 本人），在 **SQL 层强制 WHERE 条件**，禁止靠前端传参控制 |
| 字段权限 | 手机号、身份证、驾驶证、结算账户按角色脱敏；查看敏感列单独授权并**留痕** |

**SoD 职责分离冲突对（硬约束）**：审核 ≠ 财务；封号复核 ≠ 申诉仲裁；权限授予 ≠ 审计日志；价格配置 ≠ 价格审批。凡减损权益的处置**不允许单角色一键完成**。

**审计**：权限分配/修改/撤销与敏感操作写审计日志（操作人/时间/IP/变更前后值），留存 ≥180 天。

### 6.2 角色清单（按端）

| 端 | 角色 | 数据范围 |
|----|------|----------|
| 用户端 | 车主 | 本人（本人手机号可见，其余脱敏） |
| 洗车工端 | 洗车工 | 本人 + 本人订单（车主手机号虚拟号/脱敏） |
| 门店端 | 店长 / 前台 / 技师 | 本门店（结算账户仅店长可见） |
| 后台 | 超级管理员 | 全部（不含财务出款终审） |
| 后台 | 运营 / 审核 / 财务 / 客服 / 法务合规 / 城市经理 / 审计员 | 按本城市 / 全部（金额）/ 本人工单 / 只读等细分 |

### 6.3 派单六项资格谓词

**认证等级不是角色**，而是动态资格谓词。可接单判定（PRD 第 6.1 节）：

```
cert(order.items ∪ order.form) ⊆ cert_valid(worker)   // 认证覆盖订单品类与形态
  ∧ D(STORE)        // 含取送车段须有 D 证
  ∧ O(ONSITE)       // 上门单须有 O 证
  ∧ 评分达标
  ∧ 产能可用
  ∧ 未拉黑 ∧ 未封禁
  ∧ 保单有效（L1 基础保障回写成功）
```

- **判定顺序**：先认证、后评分；先硬门槛、后权重；短路判定并**全部留日志**；
- **落地位置**：派单资格中心（v6 新增）作为派单前置合取点，`xiche-service/.../learning/` 与 `.../order/` 协同；
- **可解释**：任一失败返回可解释原因与补认证/补考入口，**禁止静默不派单**；
- **合规**：认证未通过/过期/限范围属减损权益，**须人工复核 + 书面告知 + 申诉通道，48 小时内书面答复**；差评只降未来派单权重，**不扣已完单报酬、不触发资格吊销**。

### 6.4 学习考试与认证等级

| 认证 | 前置 | 解锁范围 |
|------|------|----------|
| C1 基础清洁 | 实名 + 基础 SOP | 外观清洁（STORE/ONSITE）、玻璃水补给、轮胎补气 |
| C2 标准清洁 | C1 | 标准清洁及以下、4 项轻量增值 |
| C3 精细清洁 | C2 | 精细清洁（仅 STORE）、皮革养护、发动机舱清洁 |
| D 取送车资格 | 驾驶证核验 + 实名 | 含 T1/T3 代驾段的 STORE 单 |
| O 上门作业 | C1 + 上门 SOP | 所有 ONSITE 单 |

考试规则：及格线 80 分、24h 后可补考、每期最多 3 次、服务端判定间隔、题目/选项乱序；**不采集人脸等生物识别**；证书有效期 12 个月，到期前 30 天提醒复审。

## 7. 数据模型设计要点

落点：`sql/01_schema.sql`（表结构）、`xiche-pojo/.../entity/`（实体）。

1. **主键**：自增 ID 或业务编号双键（订单号等业务键另设）；
2. **时间戳三件套**：`created_at` / `updated_at` 必备，重要表加软删除 `deleted_at`；
3. **状态机字段**：订单/支付/审核用显式状态枚举 + 流转规则，禁止字符串魔法值；
4. **金额精度**：一律整型分（`*_fen`）或 DECIMAL，**禁止浮点存钱**；
5. **快照字段**：`price_snapshot` / `rate_snapshot` 下单固化，禁止追溯改价；
6. **索引**：登录、订单列表、派单查询等高频路径建索引，外键字段必建索引；
7. **扩展预留**：只对已明确方向预留（如 Scope 数据范围字段），不为空想需求堆字段；
8. **审计表**：权限变更、认证状态、敏感操作独立留痕，留存 ≥180 天。

## 8. 非功能性基线（测试验收依据）

| 维度 | V1 基线 |
|------|---------|
| 并发 | 100~500 并发在线（超出需重新评估架构与成本） |
| 响应 | 核心接口 P95 ≤ 500ms；页面首屏 ≤ 2s（4G） |
| 可用性 | 月度 ≥ 99.5% |
| 崩溃率 | App ≤ 0.1% |
| 安全 | V1 测试环境局域网 HTTP；**生产必须全站 HTTPS**、密码哈希存储、接口鉴权全覆盖 |
| 备份 | 生产环境数据库每日自动备份 + 保留 ≥ 7 天（V1 测试版可按需） |

安全底线（生产必须满足）：密码 bcrypt/argon2 哈希；敏感字段加密；水平越权校验（资源归属）；参数化查询防注入；富文本白名单防 XSS；注册/短信/下单/优惠券防刷；关键操作日志留存 ≥ 6 个月。

## 9. 技术风险与预案（Top 3）

| 风险 | 触发条件 | 预案 |
|------|----------|------|
| 未认证/过期洗车工接单 | 短 TTL 缓存脏读、证书状态变更未及时失效 | 派单资格中心二次核对主库；状态变更主动失效缓存；失败可解释、不静默派单 |
| 缓存与数据库不一致导致改价争议 | 版本变更后追溯改动历史订单 | 订单固化 `price_snapshot` / `rate_snapshot`；禁止追溯改价；失败回源主库 |
| 模拟支付被误认为真实支付 | 文案/渠道混淆，或有人私接真实支付 | 固定橙色「模拟支付成功」文案；不接任何真实渠道；声明写入 README/DEPLOY/前端常量；生产接入须走持牌机构评审 |

## 10. 缺陷修复记录（审计报告 53 项 · 2026-11）

依据《代码审计与 v6.0 方案符合性测试报告》完成全量修复，关键变更：

| 类别 | 修复要点 |
|------|---------|
| 主链路闭环 | 支付成功后同步出 L1 ACTIVE 保单（P0-03）；考试通过 upsert 认证表并防越级（P0-04/06）；补齐 C1/C2 题库（P0-05） |
| 身份与权限 | 新增 LoginContext + AuthInterceptor，去除 Controller 硬编码身份（P0-01）；@RequireRole 三维 RBAC 与职责分离 SoD（P0-02/P1-23）；字段级脱敏（P1-24） |
| 资金 | 代垫款 D 从过账成本拆出并返还洗车工，恒等式改用 workerLaborNet 校验（P0-08）；assert 改显式校验（P1-18）；免佣卡有效费率与三级快照（P0-11/12）；三方台账与幂等语义（P0-18） |
| 订单治理 | 取消/门店接单走状态机与 CAS（P0-09/10/P1-17/22）；跨日产能重置（P0-07）；认证向下覆盖、增值项校验、工时产能、评分降权（P1-06~11） |
| 数据模型 | 证书 expire_at、局部拉黑 store_id、工位 CAS、审计 before/after、快照字段、五维评价维度（P0-14~19/P1-13） |
| 缓存 | LocalCacheService 实现 A/B/C 分级与 C 类 fail-closed（P0-13）；工位产能纠正为 C 类禁缓存（P0-14） |
| 前端 | 题库答案分散、C2 命名、E2/E3 语义修正（P1-03~05）；REST API 适配层真实消费接口+降级（P1-02） |
| 文档 | multipart-config 移至 servlet 子节点（P1-01）；DEPLOY.md JDK 表述校准（P2-07） |

**分层取舍说明（P2-02）**：V1 内测规模下，user/worker/store/catalog 等简单 CRUD 域由 Controller 直连 Mapper，核心业务规则（派单、支付、结算、审计、权限）已收敛到 Service 层。这是有意的架构取舍——避免为每个纯 CRUD 域创建空壳 Service（反而是 P2-01 批评的"空壳"问题）。生产化演进时，可按需将高价值域的业务逻辑下沉到独立 Service，不影响现有接口契约。

**文档版本**：v1.1（缺陷修复后，对应平台 v6.0 / 工程 V1 测试版）
