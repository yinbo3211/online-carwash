2.2 免佣卡公开资料与监管风险提示（直接转化为设计约束）

关键合规输入：公开资料显示，网约车/代驾行业的「免佣卡」是司机付费购买、有效期内减免抽佣的预付费权益；监管与行业自律已多次提示「买卡易、回本难」——争议集中在购买后派单减少、规则不透明、退款困难。宁波 2024 年行业自律书提出：卡期最长不超过 7 天、超期卡种停用并按实际使用情况退还余额、仅限平台自有 App 内销售；嘉兴 2025Q4/2026Q1 风险提示要求购买前明示免佣时段、订单范围、退款规则。
公开风险点本平台对应设计约束（第 4 章落地）
卡期过长、预收资金沉淀只做日卡 / 3 日卡 / 7 日卡，上限 7 天；不做月卡、季卡、年卡
买卡后不派单 / 派单锐减持卡不得降低派单权重；权重快照可审计；因评分或治理降权须与持卡状态解耦并留证据
规则不透明购买页完整明示免佣时段、适用订单范围/城市、每日免佣上限、退款规则，并留协议版本
退款困难按未使用天数/单量比例退款；平台原因全额退；后台一键退款并留痕
第三方倒卖仅洗车工端 App 内销售，禁止第三方或个人代售
宣传误导禁止「保证回本 / 稳赚 / 必赚」等承诺性与绝对化用语，附风险提示

来源：百度百科「免佣卡」词条、网易/腾讯新闻转载的行业风险提示与自律书报道（检索时间 2026-11-15）。第三方媒体对抽成比例的口径差异较大（15%–30% 不等），不作为本平台费率依据；本平台 40% 为需求方指定值，且已在 v1.0 列为 RK-04 供给风险并做成可配置。

三、结算体系 v2.0（参考代驾结构化计价）

3.1 计价模型：从「固定套餐价」升级为「结构化分项」

费用项定义与口径是否计入抽成基数 S归属
起步价按发单时段分档，含基础取送车里程与基础服务时长；分城市配置计入洗车工服务收入
洗车服务项按车型 / 套餐（外观、精洗、内饰等）定价，下单时确定计入洗车工服务收入
超里程费超出起步包含里程后，按实际行驶里程计费（轨迹为准）计入洗车工服务收入
等候费免费等候时长（建议 10 分钟）后按分钟计，设收费时长上限计入洗车工服务收入
远途费总里程超过阈值后计，设封顶金额（补偿返程）计入洗车工服务收入
时段系数夜间/高峰按配置系数调整起步价，设调价上限；系数与取值后台版本化计入洗车工服务收入
代垫费用停车费、路桥费等，凭票实报实销，不产生不收取不计入全额给洗车工
基础保障费 I_baseL1 每单强制，平台统保成本，明示内含不计入代收代付至出单方
增值保障费 I_addL2 用户自愿加购，单独计价不计入代收代付至出单方
优惠券抵扣平台营销成本，用户实付减少不计入平台预算承担
口径要点：抽成只作用于「平台定价的服务项 S」；代垫、保险费、优惠券一律不参与抽成。S = 起步价 + 洗车服务项 + 超里程费 + 等候费 + 远途费 + 时段调整。此规则写成显式纯函数并配单测，禁止运行时推断（第 6 章给出完整公式）。

3.2 分城市 / 分时段费率配置

沿用 v1.0 t_sys_config 的「配置键 + 版本 + 生效时间 + 操作人 + 变更原因」结构，新增费率组：fee_rule.city_code / time_bucket / base_price / included_km / included_min / per_km / wait_free_min / wait_per_min / long_trip_threshold / long_trip_cap / surge_cap。订单创建时固化费率版本快照，服务期间费率调整不影响本单；所有配置项为建议占位值，需业务定稿，本文不编造具体金额。

3.3 预估价预支付 → 实际结算 → 多退少补

节点规则
预估下单时按套餐、时段、城市与预估里程生成预估价，展示分项明细并锁定优惠券
预支付用户按预估价支付（V1 为模拟支付）；生成预支付单与幂等键
采集以轨迹与节点时间戳为准采集实际里程、等候时长、代垫（凭票）
实结服务完成、还车确认后计算实际应付；生成实结单（独立幂等键）
差额实付 < 预估 → 原路退回差额；实付 > 预估 → 补扣须用户确认且设补扣上限（可配置），超限转后台人工处理；差额单独立幂等
对账预支付单 / 实结单 / 差额单 / 分账指令 / 结算单五单勾稽，差异挂起 ≤24h 告警

4.2 核心规则

规则设计
生效与快照购买成功按配置生效（即时或次日 00:00）；订单创建时固化 card_snapshot（卡 ID / 卡费率 / 生效区间 / 剩余免佣单量），禁止结算时动态判定，避免卡过期或退卡追溯改价
适用范围明示购买页必须完整展示：免佣时段、适用城市与订单类型、每日/卡期免佣单量上限、是否与其他活动叠加、退款规则，并留协议版本与勾选记录
保险费不减免免佣只免平台运营费；L1 基础保障费照收照缴，L2 加购不受影响（保险是成本项，不可被权益冲抵）
派单公平承诺持卡洗车工的抢单可见性与指派权重不得因持卡而降低；每次指派保存权重快照供审计；若因评分/治理降权，须与持卡状态解耦、单独留证并可在申诉中查证
叠加规则免佣卡与优惠券可同时生效（券由平台承担，卡减免平台运营费），二者不重复扣减洗车工结算；同一洗车工同时仅 1 张生效卡
退款按未使用天数或剩余免佣单量比例退款；平台原因（系统故障、误封、无法接单）全额退；后台一键退款并留痕；退款冲回已抵扣的免佣金额需按单回溯
销售渠道仅洗车工端 App 内销售，禁止第三方或个人代售
防刷与风控单卡免佣单量上限、异常订单（自买自卖、虚假完单、短里程高频）拦截、免佣单不计入其他冲单奖励基数、卡费收入与减免额日对账
财务口径卡费为平台预收收入，按卡期递延或按实际免佣单分摊确认（需财务定稿）；免佣减免额作为权益成本单独统计，不是现金流出
合规文案禁止「保证回本 / 稳赚 / 必赚 / 最划算」等承诺性与绝对化用语；购买页附风险提示「实际收益受订单量、适用规则影响」

五、用户端优惠券

5.1 券类型与生命周期

类型说明典型发放
满减券 / 无门槛券固定金额抵扣，可设最低订单金额门槛新人礼包、运营活动

生命周期：券模板（后台配置）→ 发放/领取生成券实例（绑定用户、面额、门槛、有效期、适用城市与套餐、状态）→ 下单锁定 → 支付成功核销 → 退款按规则退回 → 过期失效。

5.2 核销与叠加规则

  • 下单页自动匹配最优可用券并允许手动更换；资格校验：门槛、品类、城市、有效期、用户身份、券状态，服务端强制执行。
  • V1 每单限用 1 张券；与免佣卡可叠加（作用于不同主体）；与其他营销活动的叠加关系后台可配置。
  • 券在预支付时锁定，支付成功核销；支付失败/订单取消释放锁定，避免券被占用。
  • 退款：未支付或全额取消 → 券退回（有效期不延长）；已完成后的部分退款 → 建议不退券、改发等值补偿券（需业务确认口径），避免资损与套利。

5.3 金额分摊：方案对比与推荐（关键决策）

方案做法对洗车工与免佣卡叠加结论
A 平台承担（推荐）券减少用户实付，洗车工结算仍按原价 S 计算；券额记入平台营销成本，不进订单分账恒等式收入不受影响简单：卡减平台运营费、券由平台预算出，二者不冲突推荐
B 按实付分摊抽成基数改为优惠后实付，洗车工与平台按比例共同承担优惠收入被摊薄，易引发不满与免佣卡叠加时公式复杂、易算错，且监管对「低价单挤压司机收入」已有提示不选
推荐 A 的理由：营销成本归属清晰、洗车工收入可预期、与免佣卡不互相冲抵、对账恒等式简单；代价是平台需设营销预算上限与熔断。B 在 40% 抽成基础上进一步压低司机实收，与 v1.0 的 RK-04 供给风险叠加，故排除。

5.4 防刷、预算与后台

领取限频（账号/设备维度）、券预算上限与日消耗熔断、异常核销告警、券与订单/用户/设备关联留痕；后台模块：券模板管理、发放与定向投放、预算与消耗、核销明细、效果看板（核销率、拉新/复购、补贴成本、券后实付）。数据表：t_coupon_template、t_coupon_instance、t_coupon_use_log、t_coupon_budget；订单新增 coupon_snapshot。

六、结算公式与恒等式（v2.0 统一口径）

① 服务费　S = 起步价 + 洗车服务项 + 超里程费 + 等候费 + 远途费 + 时段调整（代垫 R 单列，不抽成）

② 实际费率　effective_rate = card_snapshot.active ? card_rate : base_rate(40%)

③ 平台运营费　platform_fee = ROUND(S × effective_rate, 2)

④ 洗车工结算　worker_net = S − platform_fee + R（R 为凭票代垫，全额给洗车工）

⑤ 用户实付　P = S + I_base + I_add + R − coupon_amount

⑥ 分账恒等式　platform_fee + worker_net + I_base + I_add = S + R + I_base + I_add（券额由平台预算承担，作为营销成本单独记账，不进入分账指令）

⑦ 免佣减免　card_discount = ROUND(S × base_rate,2) − platform_fee（权益成本统计口径，非现金流出）

⑧ 差额　diff = P_actual − P_prepaid；diff < 0 原路退回，diff > 0 经用户确认后补扣（设上限）

七、模拟支付与支付网关预留（V1 测试版）

7.1 设计原则

业务层只依赖统一的 PaymentGateway 抽象，不感知具体渠道。三种实现按 payment.mode = mock | alipay | wechat 由工厂注入，切换只改配置与实现类，业务代码零改动；Mock 与真实实现共用同一套领域模型（预支付单、支付单、退款单、分账指令、回调事件）与同一套状态机，保证未来切换可平滑过渡。

7.2 接口契约

方法职责Mock 实现（V1）真实实现待办
createPrepay创建预支付/下单生成 MOCK- 流水号，直接返回成功调渠道下单接口、返回支付参数
queryPay主动查询支付状态返回模拟成功状态调渠道查单，防回调丢失
notifyVerify回调验签与解析模拟回调事件（可配置延迟/失败用于测试）验签、防重放、幂等处理
refund全额/部分退款生成模拟退款单并回冲台账调渠道退款、原路退回
split分账指令生成模拟分账指令，写模拟台账持牌分账产品 + 接收方进件

契约测试：为上述 5 个方法定义同一套用例（正常/重复请求/回调乱序/失败重试/金额不符），Mock 与 Alipay/Wechat 实现跑同一套测试，切换前必须全绿。

7.3 Mock 行为与状态一致性

点击「支付」→ 生成模拟流水号 → 展示「模拟支付成功」→ 触发与真实支付一致的后继链路：模拟保单回写（未回写仍禁止派单）→ 入派单池 → 履约 → 实际费用计算与差额 → 生成模拟结算单 → 钱包入账（模拟台账）→ 三方对账（模拟）→ 资损告警。幂等、回调、主动查询、状态机、对账逻辑全部照常运行，使测试能覆盖真实业务链路而非只改一个状态位。

7.4 模拟支付页原型与文案（避免误导）

合规红线：测试版不得让界面看起来像真实收款。
  • 页面顶部常驻横幅：「测试环境 · 模拟支付 · 不产生真实资金收付」；按钮文案为「模拟支付」，结果页为「模拟支付成功」。
  • 禁止出现「已付款 / 已投保 / 已到账 / 真实保单号」等足以误导为真实交易的表述；保单展示为「模拟保单记录」。
  • 禁止接入任何真实收款账户、禁止真实收款、禁止真实提现出款、禁止真实保险出单；免佣卡购买与优惠券发放均为模拟。
  • 结算与提现只生成模拟台账；「模拟提现」按钮不发生资金转移，钱包页标注「模拟余额」。
  • 仅限内部测试，禁止对外上架、禁止开放真实用户注册、禁止对外经营；Mock 与真实环境配置及数据隔离，切换前清理模拟台账，禁止模拟数据流入真实财务对账。

页面线框：顶部测试环境横幅 → 订单金额分项（服务费 / 基础保障 / 增值保障 / 代垫 / 优惠券）→ 支付方式区（模拟支付高亮；「支付宝」「微信支付」置灰并标注「待接入」）→ 底部「模拟支付」按钮 → 结果页「模拟支付成功 + 模拟流水号 + 查看订单」。支付方式区的三个入口即为未来渠道切换的界面预留位。

7.5 能力就绪后的切换清单

  1. 申请支付资质与商户号 → 2. 实现 Alipay/Wechat Gateway 并接回调验签与主动查询 → 3. 洗车工完成分账接收方进件 → 4. 接入真实保险出单接口 → 5. 三方对账联调 → 6. 契约测试全绿 → 7. 灰度按配置切换 payment.mode → 8. 关闭 Mock、清理模拟台账 → 9. 完成 v1.0 第 13.1 节全部阻塞项后方可对外经营。
