二、缓存第一原则：先划边界，再谈命中率

这个平台不是读多写少的资讯站，而是带资金分账、工位锁位、抢单与每单保险的交易系统。把缓存当成「哪里慢就加哪里」会直接制造资损与超卖：订单状态读旧值会重复派单，工位产能读旧值会超卖工位，券/卡余量读旧值会重复抵扣，保单回写读旧值会让未投保订单进入履约。因此本版先定义数据分级，再设计架构。

2.1 三级数据分级（本版核心约束）

级别典型数据是否可缓存一致性策略违反后果
A 可缓存服务目录与品类价目、城市/区域配置、字典枚举、门店基础信息、课程/题库/SOP、首页运营位、评价聚合统计可，长 TTLCache-Aside；版本键 + 变更主动失效；TTL 30~120min + 随机抖动价格展示短暂滞后
B 短 TTL 强一致认证状态与等级、权限矩阵与角色、拉黑关系、评分、门店营业时段、脱敏后的用户基础资料可，短 TTLTTL 30~120s；变更即时失效并广播；写后读走主库；接单判定二次核对未认证接单、越权放行
C 禁止缓存资金与结算金额、分账指令、订单状态机、工位锁位与产能状态、保单回写状态、券/免佣卡余量、幂等键判定结果禁止直达 MySQL 事务；金额 DECIMAL；禁止任何副本读取重复扣款、超卖、未投保履约、资损
红线（任何排期压缩不得砍）：C 类数据禁止进入 L1/L2 任何一层。抢单与锁位若用 Redis 的 SETNX / Lua 做原子判定，其性质是实时状态存储而非缓存——必须与读加速缓存分离部署、分离监控，且不设本地副本。这条与 v1.0 的「幂等 + 对账 + 资损监控」三件套、v5.0 的 fail-closed 一脉相承。

三、多级缓存架构与读写路径（图 14）

3.1 四层与职责

L0 CDN / 静态资源承接图片、课程封面、前端静态包与静态文案，命中即返回、不进应用层；L1 应用本地缓存（Caffeine）放字典枚举、城市配置、服务目录、权限矩阵，微秒级、TTL 1~5 分钟、进程内不共享；L2 分布式缓存（Redis Cluster）放会话令牌、门店信息、认证状态、题库，集群高可用、TTL 基础值加随机抖动；L3 MySQL 主从是最终真值，承载订单、结算、资金、证据、产能状态与审计。

3.2 读写路径与一致性

读链路用 Cache-Aside：逐层向下查，命中即沿层返回，未命中才下沉，DB 取值后自下而上回填。写链路统一为「先写 MySQL → 删各级缓存 → 延迟双删（100~500ms）→ binlog/CDC 兜底修复」，避免「读-写-读」并发下的旧值回填；价格、费率、认证规则另用版本号键，变更时主动失效并广播。

3.3 键规范

统一格式 {业务域}:{实体}:{ID}:{版本}。例：catalog:pkg:PKG-02:pv7、cert:worker:W123:cv3、store:info:S456:v2。所有键禁止固定过期时间，统一「基础 TTL + 随机偏移」；订单创建时固化 price_snapshot / rate_snapshot，缓存版本变更不影响已生成订单，禁止追溯改价。

五、权限模块：RBAC 与三维权限（图 16）

5.1 模型与角色清单

采用 RBAC0/RBAC1：用户（四端账号 + 后台子账号）→ 角色（权限集合，支持继承）→ 权限（原子动作，含菜单/按钮/接口）→ 资源；另引入 Scope（数据范围）作为角色生效边界，避免把「角色」与「范围」混成一张扁平表。新账号一律落最低权限默认角色，提权走审批并留痕。

端 / 域角色功能权限要点数据范围（Scope）敏感字段
用户端车主下单、支付（V1 模拟）、查看本人订单、评价、申诉本人本人手机号可见，其余脱敏
洗车工端洗车工抢单、接单、证据上传、考试学习、查看本人结算本人 + 本人订单车主手机号仅虚拟号/脱敏

5.2 三维权限与职责分离

功能权限：菜单可见 / 按钮可点 / 接口可调用，前端隐藏只是礼貌，后端校验才是底线，网关层与业务层双重校验。数据权限：行级隔离（全部 / 本城市 / 本门店 / 本人），在 SQL 层强制 WHERE 条件，禁止靠前端传参控制。字段权限：手机号、身份证、驾驶证、结算账户、行驶轨迹按角色脱敏，默认不展示，查看敏感列单独授权并留痕。

SoD 冲突对（硬约束）：审核与财务不得同一人；封号复核与申诉仲裁分离；权限授予与审计日志分离；价格配置与价格审批分离。这与 v1.0「封号须人工复核」、v3.0「拉黑冷静期复核 + 申诉仲裁」、v5.0「差评不得自动扣减报酬」直接对齐——凡减损权益的处置都不允许单角色一键完成。

5.3 生命周期与审计

申请 → 审批 → 生效（可带到期时间的临时权限）→ 定期复审（建议每季度）→ 回收；离职/换岗即时回收。所有权限分配、修改、撤销与敏感操作写 WORM 审计日志（操作人 / 时间 / IP / 变更前后值），不可篡改、留存 ≥180 天（建议值，与证据链一致）。越权拦截一律记审计并告警；权限矩阵是唯一事实源，禁止散落在各服务的条件判断里。

权限与认证的分工（易混淆点）：RBAC 角色决定「能进哪个端、能看哪些数据」；认证等级不是角色，而是动态资格谓词，决定「能接哪一类订单」。两者在派单资格中心合取判定，见第六章。

六、派单资格谓词与口径变更（图 17）

6.1 六项合取与判定顺序

可接单(order, worker) = cert(order.items ∪ order.form) ⊆ cert_valid(worker) ∧ D(STORE) ∧ O(ONSITE) ∧ 评分 ∧ 产能 ∧ 未拉黑 ∧ 未封禁 ∧ 保单有效。判定按「先认证、后评分；先硬门槛、后权重」顺序短路，全部判定留日志；认证状态只作候选筛选，最终接单前二次核对主库，避免短 TTL 缓存导致未认证接单（RK-41）。

6.2 这是本版唯一的流程口径变更

v1.0~v5.0 派单只校验评分/降权、产能、拉黑与抢单权重；本版把认证等级提为第一硬门槛。分账公式、三档价格、40%/35% 抽成、保险与证据链口径一律不改。未通过考试或认证过期的洗车工：对应品类订单不进入其抢单池、不被自动指派，但账号、已完单报酬与已认证范围内的订单不受影响。

6.3 可解释、可申诉、不自动定罚

任一失败须返回可解释原因与补认证/补考入口，禁止静默不派单。认证未通过、过期、限定接单范围属于减损权益的动作，禁止算法自动终局处置：须人工复核、书面告知、保留申诉通道，并在 48 小时内书面答复（沿用 v1.0 封号复核与 v3.0 申诉口径，并与第八章的合规要求一致）。差评只降未来派单权重，不扣已完单报酬、不触发资格吊销。

8.2 与既有治理链路的一致性

v5.0 已把「服务态度差适量减少订单」校准为降权（只影响未来派单权重，不扣已完单报酬），本版的认证体系与之同源：降权源于主观评价、只影响权重；资格收窄源于客观技能考核、影响可接单范围，两者都不得扣减已完单报酬、不得由算法独自终局执行。这样 v1.0 的封号复核、v3.0 的拉黑仲裁、v5.0 的 48h 书面答复与本版的人工复核共用一套工单与审计底座，不产生第二套冲突规则。
