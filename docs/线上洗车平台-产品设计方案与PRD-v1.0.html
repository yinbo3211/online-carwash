线上洗车平台 · 产品设计方案与 PRD

车主端 / 洗车工端 / 后台管理端三端一体化设计；覆盖下单派单、代驾取送车、车况证据链与保险闭环、评分治理、40% 平台抽成分账结算、实名与驾驶证准入、MySQL 持久化及真实上架合规路径。
版本 v1.02026-11-15状态：待评审 类型：完整版 PRD（资金 / 合规 / 强监管复合场景）作者：资深产品经理 Agent（司南）

0摘要与结论（先看这一页）

结论：产品逻辑可以完整落地，三端闭环成立；但"真实上架"能否通过，取决于三道合规硬门槛，而不是功能开发。 你描述的业务本质是「O2O 上门取送车洗车 + 代驾挪车服务 + 平台撮合分账」，不是单纯的洗车预约。因为洗车工会驾驶用户的机动车，平台同时踩在「代驾责任」「保险销售」「资金二清」「灵活用工税务」四条监管线上。功能可以在 1 个 MVP 内跑通，但上线前必须先解决第 0.2 节的三道门槛，否则会被应用商店 / 支付渠道 / 监管卡住。

0.1 五项关键待确认假设（已按此设计，可推翻）

#歧义点我的处理（假设）若你的原意不同，影响什么
A1「下单可选保险」与「每单必须有保险」并存拆成两层：L1 基础保障每单强制（平台统一投保，成本内含且在下单页明示，用户不可取消）+ L2 增值保障用户自愿勾选加购（提高保额/附加责任，单独计价）。若你要的是「用户必须自己勾一个保险才让下单」，则改为下单页必选单选组，且需要保险销售资质，见 5.2。
A240% 抽成基数抽成基数 = 洗车工服务收入 S；保险费属代收代付成本项，不参与抽成、不进入洗车工结算。若对订单总额（含保费）抽成，出险时会挤占赔付预算，且保费被抽走易引发合规与客诉，强烈不建议。
A3「自动分配 或者 抢单」混合模式：新单先入抢单池 T 秒 → 超时无人抢则按权重自动指派；评分低的洗车工在抢单池降权、指派权重下调，以此实现「减少订单」。若严格二选一，选纯抢单则「减少派单」惩罚失效（只能靠限制抢单资格）；选纯指派则开发量上升但体验可控。
A4洗车工与平台的法律关系按灵活就业 / 个体经营者（非劳动关系）设计：平台提供信息与结算服务，签署服务合作协议，60% 为经营收入，走合规税务方案。若认定为劳动关系，则需社保、最低工资、工伤、个税代扣代缴，40% 抽成模式与治理方式都要重做。
A5手机验证码登录「暂缓」本期只实现 手机号注册 + 账号密码登录；验证码登录的接口契约、数据表、入口位全部预留但不接通道，前端入口置灰并提示「即将开放」。若本期就要真发短信，需增加短信服务商、防刷限流、费用与备案，排期 +N 天。

另：文档中标注「建议值 / 估算 / 待确认」的数值均为设计占位，非市场调研结论，上线前需由业务、法务、保险合作方与支付机构逐项核定；我不编造行业数据与调研结论。

0.2 上架三道硬门槛（阻塞项，未解决不承诺上架排期）

① 资金二清 阻塞

用户付款若先进平台自有账户、再由平台转给洗车工，构成无证经营支付结算（二清）。必须走持牌支付机构的分账产品 / 银行存管 / 持牌分账服务商，由支付机构按指令直接分账到平台与洗车工。

② 保险出单资质 阻塞

页面上以「保险产品」形态售卖、比价、推荐需要保险兼业代理 / 经纪资质。推荐与持牌保险经纪或保险公司合作出单，平台只表述「服务已含基础保障」。同时须确认用户商业车险对非约定驾驶人是否免赔/加扣。

③ 代驾责任与证据链 阻塞

驾驶他人机动车发生刮蹭、违章、事故，责任必须有闭环：用户明确授权驾驶 + 驾驶证核验 + 取/还车强制验车拍照 + 全程轨迹 + 代驾责任险 + 争议申诉。缺证据链，纠纷与赔付无法收敛。

另一个必须正视的商业风险：40% 抽成偏高，可能压垮洗车工供给。 我不引用未经核实的市场数据，但逻辑上：抽成直接决定洗车工实收，实收决定接单意愿与留存，留存决定「抢单池有没有人抢」。因此把抽成比例做成后台可配置 + 分城市差异化 + 费率版本快照，并把「洗车工 30 天留存 / 实收时薪 / 抢单池响应时长」列为上线后核心观测指标（RK-04）。建议上线前用小范围试点做供给测算，而不是全量硬上。

0.3 一页结论

三端定位

用户端：下单 / 支付 / 保险 / 验车确认 / 评价投诉
洗车工端：准入 / 抢单 / 取送车验车 / 异常上报 / 结算提现
后台：审核 / 派单配置 / 治理封号 / 分账对账 / 保单 / 数据看板（上架必备）

资金底线三件套

幂等键 + T+1 三方对账 + 资损告警，任何排期压缩都不可砍。金额一律 DECIMAL / 分，禁止浮点。

登录注册

用户：手机号必填 + 密码登录；验证码登录预留不实现。
洗车工：手机号 + 实名 + 驾驶证（OCR + 有效期 + 准驾车型）+ 人脸活体建议。

治理分级

评分降权 → 抢单冷却 → 暂停接单 → 封号。封号必须人工复核 + 证据 + 申诉通道，禁止算法直接封号。

2二、背景、目标与商业模式

2.1 背景与要解决的问题

维度内容
业务现状车主需自行把车开到洗车店、排队等待；或找无固定保障的上门洗车，服务标准与责任边界不清。
核心方案车主线上下单 → 洗车工接单 → 到车主指定地点取钥匙、代为驾驶至洗车点、洗完开回交还 → 车主验收确认。车主全程无需到场。
解决的痛点车主省时；洗车工获得订单来源；平台通过撮合与履约保障抽取运营费。
引入的新风险驾驶他人车辆期间的刮蹭/违章/事故、车况归属争议、钥匙与车内财物安全、服务态度不可控、资金结算合规。
本方案重点把上述新风险用「证据链 + 保险 + 治理 + 分账」四条闭环产品化，而不是靠协议一句免责。

2.2 商业模式与抽成口径（关键，需财务/法务确认）

订单金额构成与分账公式 用户实付 P = 洗车服务费 S + 基础保障费 I_base（平台统保成本，明示） + 增值保障费 I_add（用户自愿勾选）
平台运营费 = S × R，其中 R = 40%（用户指定，做成后台可配置参数，按订单创建时的费率版本快照取值）
洗车工结算 = S × (1 − R)　｜　保险费 I_base + I_add 为代收代付成本项，全额流向保险出单方，不抽成、不进洗车工结算
校验恒等式：P = 平台运营费 + 洗车工结算 + I_base + I_add（分账指令必须满足，差异即资损告警）
项口径 / 规则说明
抽成对象洗车工的服务收入 S不含保险费、不含代收代付项；避免抽走赔付预算
费率配置sys_config.fee_rate 带版本号 + 生效时间 + 操作人 + 变更留痕禁止硬编码 40%；调比例不发版；历史订单按 rate_snapshot 结算，禁止追溯调整
结算周期订单完成且用户确认/超时自动确认后，T+1 进入可提现余额（建议值，待与支付机构确认）争议/事故订单冻结结算，转「异常处置」
提现洗车工实名 + 绑定本人结算账户 + 单笔/单日限额 + 幂等需配合灵活用工税务方案（代扣代缴/委托代征），见 13.1
退款按订单状态分摊退：未接单全额退；已取车按服务进度与保险是否生效分摊，退款金额以服务端计算为准支持部分退款；原路退回；退款需回冲分账并冲销保单（如可）
发票平台就运营费向车主/洗车工开具服务费发票；洗车工就其实收按税务方案处理口径需财务确认，禁止平台全额开票
红线：禁止平台代收代付再结算用户资金必须由持牌支付机构按分账指令直接清算到「平台商户号 / 洗车工子商户 / 保费专户」。平台自有账户禁止沉淀并二次转账给洗车工（二清）。详见 5.3 与 11.3。

5.2 保险方案：怎么同时满足「可选」与「每单必须有」

方案做法合规风险用户体验结论
① 用户必选购买下单页列出保险产品，用户必须选一款才允许支付高 构成保险产品销售/展示，需保险兼业代理或经纪资质；且「强制搭售」易被认定不合理差（被迫选择）不推荐
② 平台统保 + 用户可加购（推荐）L1 基础保障每单强制、平台统一投保、成本明示内含；L2 增值保障用户自愿加购中 需与持牌保险经纪/保险公司合作出单；平台文案只说「服务已含保障」，不做保险营销比价好（默认有保障，可自主升级）推荐
③ 只买平台雇主责任险平台自购一张年度雇主责任险，不按单出单高 无法证明「每一单都有保险」，出险时保单与订单无法对应，理赔与纠纷难闭环中不推荐（不满足「每单必须」）
推荐方案 ② 的落地要点
  1. 按单出单：支付成功 → 调保险合作方接口按订单投保（幂等键 = 订单号）→ 回写保单号、保额、保障起止时间；保单未成功回写则订单不得进入派单池（强校验）。
  2. 保障窗口：必须覆盖「取车 → 驾驶 → 洗车作业 → 归还 → 还车验车确认」全程，起止用服务端时间戳 + GPS，禁止只保洗车作业时段。
  3. 险种口径：需覆盖洗车工驾驶期间的车损、第三者责任、车上人员、车内财物（约定的清点范围内）；免赔额、责任上限、除外责任（如已有划痕、违法驾驶、酒驾）在下单页与协议中明示。具体险种与保额待保险合作方核定，本文不编造条款。
  4. 车险兼容：用户自有商业车险对「非约定驾驶人 / 未经允许的驾驶人」可能加扣免赔或拒赔，须在协议中明示，并由平台基础保障补足该缺口——这是代驾洗车最容易漏的一环。
  5. 增值保障：L2 单独计价、单独出单、用户主动勾选（默认不勾），禁止默认勾选或诱导勾选。

10.3 金额、抽成与结算口径（可直接写进测试用例）

规则定义
金额精度全部 DECIMAL(12,2) 或按分存 BIGINT；禁止 float/double；舍入规则统一（建议四舍五入到分，需财务确认）
计价主体服务端按 SKU + 保险项计算，前端传参不参与金额计算
抽成platform_fee = ROUND(amount_service × rate_snapshot, 2)；amount_net = amount_service − platform_fee；保险费不参与抽成
恒等式amount_total = platform_fee + amount_net + amount_ins_base + amount_ins_add，分账指令必须相等，差异即资损告警并阻断
幂等支付 / 分账 / 退款 / 提现 / 投保 / 抢单：幂等键 = 业务单号 + 场景 + 渠道流水号；重复请求返回首次结果，禁止重复入账或重复接单
对账T+1 对支付渠道、保险出单方、洗车工结算三方逐单核对；差异单挂起、≤24h 超时告警；差异处理留痕，禁止自动平账
资损告警（四类起）重复支付 / 负金额或超额 / 状态回跳 / 对账差异与分账金额不符；建议 ≤5 分钟触达
退款原路退回，支持部分退款；退款金额按服务端分摊规则；退款必须回冲分账、冲销/标记保单、冲销结算；幂等防重复退
冻结异常处置 / 投诉未结 / 申诉中的订单，结算状态 = FROZEN，处置完成后释放或按结果调整

11.3 资金安全底线三件套（不可砍）

③ 资损监控

15.2 关键页面原型思路（线框描述，不含视觉稿）

用户端 · 确认订单页

目标：让用户一次看清金额、保障与授权，放心把车钥匙交出去。
布局：顶部导航（返回/标题）→ 取车信息卡（地址/时间/车辆）→ 服务套餐 → 金额明细（S / 基础保障 / 增值保障 / 合计） → 保障说明卡（L1 不可取消、L2 默认不勾、保障范围与除外责任入口）→ 协议勾选项（授权书 + 服务协议，带版本）→ 底部吸底「合计 ¥xxx · 去支付」。
交互：L2 勾选实时更新合计；未勾协议禁止支付；金额一律服务端返回；保单出单中展示进度，失败给退款/重试说明；空/载/错/界四态齐全。

洗车工端 · 取车验车页

目标：把「车交给我之前长什么样」固定成不可抵赖的证据。
布局：顶部进度（第 N/共 M 张）+ 拍摄引导示意图 → 已拍缩略图网格（缺项标红）→ 「标注既有划痕」入口 → 底部「提交验车单」（照片不齐置灰）。
交互：仅实时拍摄、禁相册；每张自动加时间戳/GPS/订单号水印；弱网本地暂存并断点续传；提交前不可点击「开始驾驶」；提交后推送车主确认，超时按规则默认通过并留痕。

后台 · 洗车工治理页

目标：让「减少订单 / 封号」有证据、有分级、可申诉。
布局：洗车工概览（评分趋势、证件有效期、近 30 天单量）→ 关联投诉与证据列表 → 处置面板（警告 / 降权系数 / 暂停 N 天 / 封号）→ 复核与告知记录 → 申诉记录与改判。
交互：选「封号」时强制上传证据 + 填写理由 + 指定复核人，缺失则提交按钮不可用；降权自动带出权重快照；所有动作写审计日志并通知洗车工端。

后台 · 对账看板

目标：资金差异一眼可见、可追、可关。
布局：日期/渠道筛选 → 汇总卡（应分账、实分账、差异单数、挂起超 24h 数）→ 差异明细表（订单号 / 来源 / 类型 / 金额 / 状态 / 处理人）→ 资损告警列表。
交互：差异单默认挂起、禁止自动平账；超时标红并升级；处理需填原因与凭证；与订单、分账指令、结算单三处可跳转核对。

可用性自检：核心任务（下单、抢单、验车、处置）关键操作 ≤3 步；每按钮有明确结果预期；表单有校验与错误定位；无死链；危险操作（封号、退款、提现）二次确认；关键操作可返回/取消；文案无歧义、无诱导、无绝对化用语。
